# Чистая тестовая база Supabase на VDS

## Решение (16.10.2026)

Для тестирования нового self-hosted Supabase **не переносим старые персональные данные**: пользователей Auth, профили учеников, сообщения, платежи, занятия и историю. Создаём **новую отдельную тестовую БД со структурой приложения**. Облачная production-база остаётся источником истины; приложение пока использует её.

## Что нужно сохранить в новой БД
- Стандартные системные схемы/роли Supabase Auth/Storage/PostgREST из штатной установки целевого образа.
- Структуру всех прикладных таблиц public, индексы, sequences, constraints, FK, функции, триггеры и RLS политики, проверяя соответствие инвентаризации архива: 30 таблиц, 51 функция, 16 триггеров, 44 FK, 60 policies.
- Все прикладные настройки, необходимые для работы PWA. Отдельно установить Storage buckets metadata для тестовой среды, **без старых файлов**.
- Создать отдельных тестовых пользователей через Auth API **после** проверки схемы. Пароли и учетные записи production не использовать.

## Как строим схему
1. Поднять **новое независимое тестовое окружение**; нельзя перезаписывать действующую БД `supabase-db` или ранее созданные лабораторные тома.
2. Применить эталонные versioned migrations из репозитория, определив порядок и дедупликацию имён (проверка 68 SQL-файлов). Для объектов, отсутствующих в миграциях, использовать тщательно проверенный schema-only экспорт/TOC из cloud-backup.dump, **исключив системные схемы и все данные**.
3. Согласовать зависимости от auth.uid(), storage, extensions; исключить планировщики cron, pg_net calls, Vault secrets, внешние HTTP, OneSignal и live Edge Functions. Наличие `--network none` не заменяет проверки SQL на побочные эффекты.
4. Установить корректных владельцев, GRANT, default privileges, проверить реальное поведение RLS под anon/authenticated. Исходный dump создан с `--no-owner --no-acl` — автоматическое восстановление прав невозможно.
5. Проверить создание тестового пользователя, логин, CRUD таблиц, Storage bucket и основные сценарии UI на **отдельном тестовом URL/конфигурации**. Не перенастраивать production `VITE_SUPABASE_URL` до отдельного разрешения.
6. После проверки схемы решить отдельно, нужна ли миграция данных позднее. Переход на чистую базу в production **не производится автоматически**.

## Критерии готовности
- [ ] Системные сервисы test stack healthy.
- [ ] 30 таблиц public и зависимости соответствуют исходной структуре либо различия документированы.
- [ ] Сравнение 51 функций, 16 триггеров, 60 RLS policies, 44 FK и тесты прав.
- [ ] Auth: создание и вход тестового пользователя, без старых пользователей.
- [ ] Storage: работа тестового bucket с нуля, без старых файлов.
- [ ] Никаких отправленных production уведомлений.
- [ ] Положительные и отрицательные smoke тесты, документированный rollback.
- [ ] Тестовая среда изолирована; исходная автошкола продолжает работу.

## Отложено
- Импорт 28 пользователей Auth и 28 профилей из облачной базы.
- Обход несовместимости `auth.audit_log_entries.ip_address` в старом архиве.
- Перенос истории сообщений, занятий, финансовых записей и бинарных файлов Storage.
- Production cutover и PR #169.

**Внимание:** новая пустая БД не является переносом существующей автошколы. Если когда-нибудь использовать её как production, старые ученики и данные там отсутствуют.
