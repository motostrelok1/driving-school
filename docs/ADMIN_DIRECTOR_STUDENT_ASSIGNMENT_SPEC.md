# ADMIN-OWNERSHIP-01 — закрепление учеников за администраторами и роль директора

**Статус:** запланировано, без реализации. **Контур:** Driving School PWA, Supabase schema/RLS, задачи, сообщения, уведомления, кабинеты. Вне текущей миграции и без изменений production.

## Цель
У каждого ученика есть назначенный ответственный администратор. Его сообщения, новые и незавершённые задачи маршрутизируются этому администратору, не попадая в общую кучу. По умолчанию обычный администратор **видит только своих учеников**. Директор назначает администраторов, управляет правами и может просматривать всех.

## Роли и доступ
- **director** — новая прикладная роль (не service_role): полный надзор за учениками, администраторами, чатами и задачами в рамках организации; назначает и переназначает ответственных, задаёт разрешения, видит журнал изменений. Создание первого директора — только защищённым bootstrap, пользователь не может сам себе повысить роль.
- **admin** — по умолчанию только ученики, за которых отвечает, и связанные с ними карточки, документы, платежи, чаты, назначения и задачи. Разрешённое расширение видимости (все ученики / конкретные группы / другие администраторы) устанавливает только директор. Раздельно управлять правом **видеть** и **изменять/переназначать**.
- **instructor / student** — существующие роли и изоляция не ослабляются. Бывший инструктор не получает доступ к закрытым чатам.

## Назначение ученика
- Основной ответственный администратор у ученика — один, с возможностью отдельной роли временного замещения, если понадобится после проектирования.
- Новый ученик попадает в «Не распределены» директору, пока тот не назначит ответственного. Это исключает утечку уведомлений всем администраторам.
- Массовое назначение, фильтрация по группе и ответственному, счётчики нагрузки; при увольнении/деактивации администратора обязательный сценарий передачи учеников и открытых задач.
- История смен ответственностей: кто, кого, кому, когда, причина, количество перенесённых открытых задач/чатов; аудит нельзя изменять клиентом.

## Маршрутизация событий
- Все **новые** адресные задачи ученика (включая автоматические события теории, вождения, документов и оплат) назначаются ответственному администратору, а не всем admins.
- Все **открытые/невыполненные** задачи при смене ответственного атомарно передаются новому администратору; завершённые остаются в истории с первоначальным исполнителем. Не допускаются двойные push, дубликаты задач и потеря assigned-to.
- Уведомления о сообщениях из активных ученических чатов приходят новому ответственному. Старый администратор после передачи перестаёт получать новые сообщения/push и не должен видеть чат, если директор не разрешил отдельную расширенную видимость.
- Общесистемные задачи (без ученика), аварии и события самого директора — отдельная очередь, не маршрутизируются автоматически по ученику. Для ученика без ответственного события попадают в безопасную очередь директора.

## Переназначение и чаты
- Директор меняет ответственного через проверяемую серверную RPC/транзакцию, не через доверенный клиентский UPDATE.
- Новый администратор присоединяется ко **всем текущим открытым чатам** назначенного ученика, получает доступ к предыдущему контексту внутри них и становится обязательным администратором-участником; старый администратор исключается из активных участников и теряет право чтения/отправки, если нет отдельного разрешения.
- История сообщений и закрытые чаты неизменна. Запрещено повторно открывать закрытый при смене инструктора чат; для новой ситуации создаётся новый чат по действующим правилам.
- В беседе добавляется **системное событие** «Ответственный администратор изменён», видно участникам. Учитывать уникальность участников, блокировку конкурирующих изменений и RLS для history/notifications.
- Ученику и инструктору не нужно вручную создавать чат: его по-прежнему создаёт администратор/разрешённый серверный процесс, пользователь и инструктор могут отвечать в доступном открытом чате.
- Проверить существующую схему thread participants, message recipients, пушей и админ-студент-инструктор RPC до определения точных SQL изменений.

## Настройки директора
- Управление видимостью конкретного admin: «только свои» (default), «назначенные группы», «все ученики» (отдельное привилегированное разрешение); модель расширяемая, минимально необходимые права по умолчанию.
- Отдельные флаги: может видеть чужие задачи, может принимать/передавать задачи, может создавать чаты, может управлять расписанием, документами и оплатами. Не приравнивать видимость к разрешению выполнять действия.
- Панель директора: распределение учеников, нагрузка и SLA по задачам, фильтры, поиск, переназначение, журнал доступа и кадровых изменений.

## Техническая спецификация (этапы)
1. Аудит миграций: profiles.role check/enum, is_admin, все RLS policies и security-definer RPC, маршруты и role guard frontend, чат participants/recipients, Tasks, Edge Functions и триггеры. Проектировать директорский доступ централизованно, не заменять механически `is_admin`.
2. Миграции: assignments (student_id, admin_id, valid_from/to) и immutable audit; privileges/policies, индексы по ответственному и статусам задач. Подготовить совместимость с существующими данными и ручную защищённую процедуру начального распределения.
3. Transactional RPC: назначение/переназначение, перенос открытых задач, замена админ-участника открытых чатов, перенастройка получателей будущих уведомлений, outbox/idempotency. Проверить недопустимые состояния и откат при ошибке.
4. Директорский UI и ограничения списка студентов/карточек/поиска; «Мои ученики», «Мои задачи», «Не распределены»; пустые состояния и история передачи.
5. Edge push, cron и уведомления только текущему ответственному; удалить широковещательную логику там, где событие относится к ученику.
6. Регрессионные тесты: роли director/admin1/admin2/student/instructor, изоляция данных по REST/RPC/Storage/Realtime (не только UI), событие в чате, смена инструктора и закрытый чат, задача до/после передачи, concurrent reassign, deactivated admin и сценарий без ответственного.
7. Внедрение: сначала на test Supabase, затем бэкап и согласованный rollout на production с явным migration gate. Feature flag / безопасный переходный режим: до назначения ответственных не скрывать внезапно операционные задачи, а предоставлять директору очередь нераспределённых.

## Критерии приёмки
- Два обычных админа без расширенных разрешений не видят чужих учеников, документов, чатов, задач или адресных уведомлений через UI и прямые API.
- Директор видит всех и может переназначать; обычный админ не может сам выдать себе права или изменить чужого ответственного.
- В момент переназначения все незавершённые задачи, новые сообщения/уведомления и доступ к **открытым** чатам переходят новому администратору без потери истории; предыдущий не получает новые адресные push.
- Закрытые чаты остаются закрытыми; события и история участников корректны.
- Пользователи без ответственного попадают в директорскую очередь, не в общую рассылку.
- Нет регрессии доступа учеников/инструкторов и функций вождения/теории; DB-RLS проверена.
