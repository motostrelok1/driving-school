# Карта зависимостей восстановления Supabase (тестовая среда)

Дата: 2026-10-16. Статус: **план; не запускать полный restore**.

## Факты из проверок

- Архив `cloud-backup.dump` PostgreSQL 17.6 custom, 921743 байта, снимок 07:38:25 UTC.
- TOC: 30 таблиц public и 30 секций их данных; 27 секций auth; 51 функция public; 60 policies; 16 triggers; 44 FK; 8 секций storage; 12 записей extensions.
- Отдельный no-network smoke-test успешно восстановил 28 записей `public.profiles`; это **не** подтверждение входа пользователей или RLS.
- Production self-hosted PostgreSQL работает отдельно и не менялся.

## Фазы полной проверки

### 1. Штатный bootstrap системной БД

Создать **новый** кластер из точного образа `supabase/postgres:17.6.1.136` в отдельном контейнере и томе, с учётом init-скриптов именно этого образа. Ранее найденные файлы:
- `00000000000000-initial-schema.sql`: системные роли и grants; роль `supabase_admin` в нём **используется**, а не создаётся (возможен bootstrap через `POSTGRES_USER=supabase_admin`).
- `00000000000001-auth-schema.sql`: базовая схема Auth.
- `00000000000002-storage-schema.sql`: базовая схема Storage.
- `00000000000003-post-setup.sql`: служебные права.

Прежде чем запускать, проверить всю цепочку штатного entrypoint/migrate.sh, порядок файлов и требуемые роли/extension preload. Не считать, что запуск с `POSTGRES_USER=supabase_admin` автоматически гарантирует успех: отдельные миграции и сервисные настройки могут требовать ещё объектов.

### 2. Строгая изоляция

Сеть Docker `none` и без опубликованных портов. Выключить preload и планировщики `pg_cron`, `pg_net`; отдельно убедиться, что штатный bootstrap не требует запуска этих фоновых процессов. Не копировать cloud cron jobs, net request queues, webhooks, Vault secrets, OneSignal ключи, SQL с опасными побочными эффектами. Не запускать Supabase Auth/Storage/Edge runtime и приложение против тестовой БД до проверки изоляции.

### 3. Отбор TOC и стратегия данных

Из-за уже существующих штатных схем `auth` и `storage` **не следует просто накатывать системную schema-only часть облачного dump поверх bootstrap**. Разделить:
- системные объекты: роли, расширения, schema baseline — из целевого образа;
- данные `auth.users`, `auth.identities`, связанные auth таблицы — выборочно с учётом FK и целостности;
- `public`: структура, данные, функции, политики, триггеры — в зависимостном порядке, проверив обращения к auth/storage/vault;
- `storage`: только metadata после проверки совместимости версии и отдельно сами файлы;
- исключить технические схемы `cron`, `net`, `realtime`, `pgbouncer`, служебные статистики и публикации до отдельного решения.

Важное отличие: исходный backup создан с `--no-owner --no-acl`. Полное восстановление само по себе НЕ вернёт все ownership/grants; для корректного RLS и работы сервисов нужен отдельный валидированный grants/ownership этап.

### 4. Верификация

Проверять не только COUNT:
- Auth: UUID, целостность users/identities, password hashes, типы подтверждений, отсутствие дубликатов.
- Public: 30 таблиц и их данные, 51 функция, 60 policy, 16 triggers, 44 FK, sequences, constraints.
- RLS: фактические права и отрицательные тесты от имени anon/authenticated.
- Storage: 8 секций metadata и 4 бинарных объекта бакета `pdd-course-media` (файлы не входят в pg_dump).
- Вход Auth и JWT через отдельный безопасный тестовый сервис только после подготовки; не отправлять реальные SMS/e-mail/push.
- Сверить свежесть: snapshot устаревает по мере работы облачной автошколы; непосредственно перед cutover нужен новый согласованный backup.
