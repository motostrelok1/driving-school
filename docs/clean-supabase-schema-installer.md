# Чистая тестовая Supabase БД (без облачных пользовательских данных)

Сценарий: `scripts/create-clean-supabase-test-db.sh`. **Пока не запускается CI автоматически.**

## Что создаётся
- Изолированный, новый `clean-supabase-schema-lab-v1`.
- Отдельный новый Docker volume `clean-supabase-schema-lab-data-v1`.
- Штатный bootstrap PostgreSQL/Supabase из `supabase/postgres:17.6.1.136`.
- **Только схема public** из существующего архива: DDL таблиц, функций, индексов, внешних ключей, триггеров и политик. Исключены TABLE DATA.
- Системные схемы auth/storage остаются из штатной установки, без старых пользователей или записей.

## Что не создаётся
- Ученики, преподаватели, пользователи Auth, занятия, оплаты, переписка, события.
- Файлы и метаданные существующего Storage.
- Действующая тестовая PWA/полноценный API endpoint: пока только PostgreSQL-контейнер без сети. Это не готовый тестовый Supabase сервер.
- Изменения рабочей базы `supabase-db` или переключение приложения.

## Ограничения и возможные сбои
- Archive DDL может содержать функции/типы, зависящие от расширений и схем, отсутствующих в целевой установке. На первом несовпадении скрипт останавливается, сохраняя только новые test artifacts.
- Объекты из dump были сохранены с `--no-owner --no-acl`: grants и ownership не восстанавливаются. Нужно дополнительно построить/проверить правильные права и RLS. Не публиковать test stack в Интернет до проверок.
- Schema-only экспорт не переносит `storage.buckets`; тестовые buckets создаются через Storage API позже.
- `--network none`, отсутствие портов, запрет повторного использования существующих имён. Не присоединять контейнер к сети ради обхода ошибок.
- Даже при `SCHEMA DDL APPLIED` полнота структуры не доказана до сравнения функций/ограничений и функциональных тестов.

## Порядок
1. Review скрипта и зелёные статические проверки PR.
2. Один ручной запуск root на VDS, не предоставляя GitHub CI общий доступ к Docker.
3. Проверка DDL и исправление схемных зависимостей в отдельном тестовом окружении.
4. Поднятие отдельного тестового Auth/PostgREST/Storage и создание синтетического администратора через API.
5. Позитивные и отрицательные тесты прав, RLS, пользователей, бронирования, Storage.
6. Отдельное решение о дальнейшей судьбе тестовой БД. Не подключать production автошколу без согласования.

Исторический PR #185 для импорта старых Auth записей к этому пути не относится. PR #169 с production миграциями не применяется.
