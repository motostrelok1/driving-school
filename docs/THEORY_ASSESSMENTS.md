# Официальное тестирование: этап 1

Администратор открывает «Пользователи» → карточка ученика → иконка «Тестирование».
В окне можно назначить промежуточный зачёт или внутренний экзамен, увидеть назначения и отменить назначение до начала попытки. Новое назначение не перезаписывает предыдущие записи.

Зачёт: темы ПДД, 1–800 вопросов, 1–180 минут, допустимые ошибки меньше количества вопросов, открытие и дедлайн. Внутренний экзамен: фиксированный шаблон автошколы — все темы, 20 вопросов, 20 минут, не более 2 ошибок. Это внутренний стандарт, а не заявление о соответствии процедуре государственного экзамена. Даты вводятся/отображаются по Москве и сохраняются как `timestamptz`.

## Установка после merge

1. На сервере выполнить:

   ```bash
   cd /var/www/driving-school && git pull --ff-only origin main
   cat supabase/migrations/0034_theory_assessments.sql
   ```

2. Скопировать весь SQL, показанный командой `cat`.
3. В Supabase открыть проект `dznjopipisdfrojlpxrz` → **SQL Editor** → **New query**, вставить SQL и нажать **Run**. Миграцию применять один раз. Она выполняется в транзакции.
4. На сервере выполнить:

   ```bash
   cd /var/www/driving-school && npm run build
   ```

5. Открыть `https://dvizh-school.ru` под администратором → **Пользователи** → раскрыть карточку ученика → **Тестирование**. Назначить зачёт, перезагрузить страницу и проверить сохранённые темы/параметры/сроки. Затем проверить фиксированные настройки экзамена и отмену назначения.

Edge Functions в этом этапе обновлять не нужно.

## Схема и доступ

- `theory_assessments`: неизменяемые параметры назначения, автор, ученик, московские сроки в UTC и отметка отмены.
- `theory_assessment_attempts`: одна попытка на назначение, снимок вопросов и правил, серверное начало/окончание/лимит, итог. `answer_key` хранится отдельно и недоступен через клиентские `SELECT`.
- `theory_attempt_answers`: отдельные ответы с уникальной парой `(attempt_id, question_index)`.

Ученик читает только свои записи; администратор читает все; инструктор и аноним не имеют доступа. Клиенты не могут напрямую создавать, менять или удалять назначения, попытки и ответы. Назначение и отмена идут через RPC `admin_assign_theory_assessment` / `admin_cancel_theory_assessment` с серверной проверкой администратора. Повтор одной формы с тем же UUID и параметрами возвращает существующее назначение. Изменение параметров с уже сохранённым UUID запрещено.

Удаление учётной записи ученика удаляет его записи тестирования вместе с профилем, как остальные связанные данные. Удаление автора назначения оставляет назначение с `created_by = null`.

## Следующие этапы

Прохождение в `/student/theory/testing`, создание/восстановление попытки, запись ответов и расчёт результата появятся в PR 2. Тогда же отправляется уведомление ученику о назначении. Существующий тренировочный экзамен остаётся самостоятельным режимом.

Для PR 2 требуется доверенный серверный банк с привязкой вопросов к темам: в текущем JSON такой привязки нет. Нельзя принимать правильные ответы или итог из браузера. При старте блокировать строку назначения `FOR UPDATE`, затем проверять отмену, сроки и существующую попытку. Снимок вопросов не должен включать правильные ответы и подсказки. Пересдача создаётся новым назначением, а не очисткой старой попытки.

Развёрнутая история, состояния иконки, уведомление администратору и задачи по неуспешным попыткам запланированы в PR 3.

## Проверки

`npm run build` и `npm run lint`.

`supabase/tests/theory_assessments.sql` запускается после миграции в отдельной тестовой PostgreSQL/Supabase БД с ролями `anon`, `authenticated`, `service_role`, таблицами `auth.users`, `profiles` и функциями `auth.uid()`, `is_admin()`. Проверяет RLS и column grants с переключением ролей, запрет записи результатов, идемпотентность, параметры, отмену, уникальность попыток и ограничения снимка. Тестовые данные откатываются транзакцией.
