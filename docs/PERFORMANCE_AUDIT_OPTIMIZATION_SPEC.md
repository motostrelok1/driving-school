# Производительность PostgreSQL / Supabase и React: аудит и оптимизация

**Статус:** запланировано, реализация не начата. **Приоритет:** после проверки корректности профиля курсанта; до масштабирования нагрузки. **Зона:** только `dvizh-school.ru` и его Supabase. Не изменять сайты `edu.dvizh-school.ru` и `lms.dvizh-school.ru`. Не пересекаться с работой по самостоятельному Supabase CI/CD (PR #169).

## Цели и ограничения
- Уменьшить p50/p95 времени загрузки расписания, профиля, теории, сообщений и времени ответа запросов при реальной многопользовательской нагрузке.
- Не путать сетевой RTT («пинг») и задержку SQL + API + браузерного рендеринга. Сначала измерить каждый участок.
- Сохранить корректность RLS, доступа по ролям, броней, списания академических часов, отмен, push, прогресса, публикаций.
- Не оптимизировать «на глаз»; каждое изменение должно иметь воспроизводимый замер и сценарий отката.

## Этап 0. Базовая линия и инвентаризация (чтение, без изменений)
1. Карта вызовов `supabase.from/rpc/auth`, Edge Functions и REST по страницам; перечень `useEffect`, таймеров, подписок Supabase Realtime, повторных запросов.
2. Измерить в DevTools Network для мобильного и десктопа: waterfall, DNS/connect/TTFB, payload, число обращений после открытия страницы и за 1/5 мин ожидания, p50/p95.
3. Проверить географию клиента и сервера, сетевую задержку, CPU/RAM/IO/диск, pg_stat_activity, блокировки, число активных/ожидающих соединений, pooler, RLS policies.
4. SQL только на чтение: `pg_stat_statements` (если доступно), `pg_stat_user_tables`, `pg_stat_user_indexes`, `pg_stat_activity`, `pg_indexes`, размеры таблиц, примерные сканы и задержки. Не публиковать тексты с личными данными, токены, IP, пароли, ключи. Снимать планы `EXPLAIN (ANALYZE, BUFFERS)` только для безопасных SELECT и на согласованной нагрузке; не запускать ANALYZE для DML на production.
5. Инвентаризация количества записей и индексов критичных таблиц без выгрузки персональных данных.

## Этап 1. Ранжирование запросов
- Выделить top N по суммарному времени, p95, частоте, строкам/байтам и конкурентности; отличить медленный SQL от чрезмерно частых быстрых запросов.
- Приоритетные страницы: сетка расписания ученика (в т.ч. частота рефетча), расписание админа и инструктора, профиль курсанта и подсчёт часов, список и история чатов/уведомлений, PDD уроки и прогресс.
- Проверять фильтры по `student_id/instructor_id/start_at/status`, сортировки, pagination, N+1, дублирующиеся загрузки, размер payload, зависимость React hooks.

## Этап 2. Оптимизация SQL и схемы (после аудита)
- Добавлять составные/частичные индексы **только** под реальные WHERE/JOIN/ORDER BY и EXPLAIN. Проверить дублирование существующих индексов, цену INSERT/UPDATE и размер.
- Переписать выявленные медленные выборки, уменьшить `select('*')`, внедрить безопасную серверную агрегацию, лимиты и пагинацию.
- Оценить RLS под нагрузкой и индексы по полям политики; не обходить авторизацию ради скорости.
- Для каждого DDL: проверить совместимость с Supabase, блокировки, развёртывание в низкую нагрузку, резервную копию, откат. Не запускать SQL без отдельного согласования. Изменения проводить только через отдельные миграции, согласовав с параллельным потоком CI/CD.

## Этап 3. React / Supabase
- Сократить polling там, где это корректно: адаптивный интервал, пауза в скрытой вкладке, обновление после мутаций, фокуса и события. Рассмотреть Realtime только после расчёта нагрузки и правильной авторизации/очистки подписок.
- TanStack Query или действующее кеширование: дедупликация, staleTime, инвалидация только затронутых ключей, AbortController, защита от гонок.
- Профиль: параллелить независимые маленькие выборки, не скачивать полный курс ПДД для одного счётчика, устранить дубли, кешировать справочники категорий.
- Теория: разделённая загрузка каталога/раздела и медиа; пагинация тяжёлых списков; lazy load изображений.
- Критично: бронь и доступность слотов всегда перепроверяются на сервере перед подтверждением; кеш не является источником истины.

## Этап 4. Проверка эффектов и регрессии
- Повторить измерения тех же действий, сравнить p50/p95, число запросов/мин, SQL total time, rows/bytes, CPU/RAM/IO, ошибки. Целевые значения установить **после baseline**, без выдуманных процентов ускорения.
- Проверить 1/10/50/100 конкурентных пользователей (по возможностям стенда); производственные нагрузочные тесты только согласованно и с ограничениями.
- Сценарии student/instructor/admin: бронь одного слота двумя клиентами, перенос/отмена, списание часов, прогресс ПДД, сообщения и пуши, смена инструктора, 7-дневное расписание, мобильная сеть и скрытая вкладка.
- Линтер, TS, сборка, тесты; проверить отсутствие лишних SQL и утечек подписок; rollback для каждого PR.

## Порядок PR и критерии готовности
- **PERF-1:** наблюдаемость и отчёт baseline + список узких мест с измерениями (без мутаций БД).
- **PERF-2:** оптимизация частоты сетевых обращений + кеширование, отдельные PR по зонам.
- **PERF-3:** SQL/индексы по доказанным bottleneck, миграции согласуются с владельцем CI/CD.
- **PERF-4:** сценарные и ограниченные нагрузочные проверки; документ до/после, алерты.

Готово, если: устранены наиболее дорогие подтверждённые bottleneck; измерения до/после приложены; нет ухудшения p95 и бизнес-логики; сохранены RLS, push, история и публикация; изменения прошли CI и функциональную проверку.

## Оценка
Предварительно: аудит 1–2 ч, SQL 2–5 ч, клиент 3–6 ч, тесты 1–3 ч; **итого 7–16 ч** при простой диагностике. Это не SLA: сложная инфраструктура/миграции/параллельный CI/CD могут увеличить сроки.

## Необходимое от владельца проекта
- Доступ к GitHub для аудита исходников (есть).
- Диагностические результаты SQL и базовых метрик Supabase/сервера, **без** секретов и персональных данных.
- Отдельное разрешение на миграции и нагрузочное тестирование перед применением. До этого только безопасное чтение.

## Диагностические SQL-шаблоны (только SELECT)
```sql
-- Частота сканов / примерные строки: текущая статистика PostgreSQL
select schemaname, relname, seq_scan, idx_scan, n_live_tup
from pg_stat_user_tables
where schemaname = 'public'
order by seq_scan desc nulls last limit 30;

-- Индексы таблиц приложения
select schemaname, tablename, indexname, indexdef
from pg_indexes where schemaname = 'public'
order by tablename, indexname;
```
Проверка `pg_stat_statements` и другой диагностики требует выяснить доступность расширения и разрешения; перед выполнением избегать передачи пользовательских значений, содержащихся в текстах запросов.
