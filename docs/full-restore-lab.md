# Лабораторное восстановление Supabase — PR для оценки

Этот PR содержит **попытку восстановления** таблиц `auth`, `public` и `extensions` в отдельный контейнер, но **не подтверждённый полностью рабочий Supabase**.

**НЕ активировать этот сценарий до code review, особенно SQL из архивов и форматов Docker mount.** Скрипт не публикует порты, запускается с `--network none`, не включает `pg_cron` и `pg_net`, не использует тома основной БД. Архив закреплён только для чтения. Новый том/container имеют фиксированные имена и скрипт остановится, если они уже существуют.

Запуск выполняется вручную под root только после отдельного подтверждения. Пока намеренно **нет GitHub Actions и sudoers** для этой операции; одного успешного read-only preflight недостаточно, чтобы давать CI права на создание контейнеров.

## Известные технические риски / ограничения

- Supabase обычно требует собственного набора ролей, схем, расширений, ownership и grants. Создание только placeholder-ролей в пустом PostgreSQL **не воспроизводит** конфигурацию штатной установки. Возможны ошибки восстановления.
- В исходном дампе содержатся объекты Supabase из различных схем. Фильтр `public/auth/extensions` может пропустить зависимости, например `vault`, `storage` и глобальные настройки. Этот скрипт **не должен** использоваться для production.
- Попытка с `--single-transaction --exit-on-error` откатывает изменения внутри новой тестовой БД при ошибке, но созданные контейнер и том остаются для диагностики.
- Этот архив — снимок на определённую дату. Для переключения нужен новый свежий дамп, перенос файлов Storage и проверка Auth.
- Тестовое восстановление не должно отправлять сообщения/уведомления, инициировать HTTP или запускать cron.
- После успешной команды pg_restore проверим права, RLS, триггеры, числа строк, роль Auth, extensions, Storage, auth JWT-login, Edge Functions. Не заявлять «всё восстановлено» до независимой проверки.

## Следующий порядок

1. Проверить схему зависимостей из дампа и результаты схематической попытки.
2. При ошибке — исправить lab-инициализацию под конкретный образ и архива, а не отключать safety checks.
3. После восстановления обязательных схем — отдельный набор assertions.
4. Файлы Storage копировать отдельно; metadata в PostgreSQL недостаточно.
5. Отдельные PR для production cutover и rollback.
