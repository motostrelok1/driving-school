# Тестовый Auth и REST — первая рабочая конфигурация

Данный этап добавляет **новый** Docker Compose project `driving-school-supabase-test` с отдельным PostgreSQL volume, Auth и PostgREST. Снимок /opt/backups/supabase/cloud-backup.dump используется **исключительно для восстановления схемы public** без TABLE DATA. Тестовый Postgres с новыми секретами не подключается к `supabase-db` и не открывает порт БД на хосте.

- Единый gateway: `127.0.0.1:28000` (маршруты `/auth/v1`, `/rest/v1`, `/storage/v1`); прямые endpoint: Auth `127.0.0.1:19999`, PostgREST `127.0.0.1:18080`, Mailpit UI `127.0.0.1:18025`.
- Оба endpoint доступны только с VDS или через SSH tunnel. Внешний HTTPS не настроен.
- JWT/пароли генерируются локально и хранятся в root-only `/opt/driving-school-supabase-test/.env`; **не публикуйте их**.
- Не включены: Edge Functions, cron, OneSignal и тестовый frontend.
- Миграция прикладных прав не доказывается совпадением SQL объектов; требуются Auth login и проверки RLS через HTTP прежде чем открывать доступ.

## Что изменилось после первого рабочего запуска

1. **Триггер `on_auth_user_created` создаётся установщиком.** Восстановление из архива грузит DDL только схемы `public`, поэтому триггер на `auth.users` в дампе отсутствует. `scripts/install-test-supabase-auth-rest.sh` после restore выполняет `CREATE OR REPLACE FUNCTION public.handle_new_user()` (ФИО из `first_name`/`last_name`/`middle_name`| `patronymic`, телефон, роль жёстко `student`) и `CREATE TRIGGER on_auth_user_created`, затем проверяет наличие триггера. Без этого шага регистрация проходит, но профиль не создаётся.
2. **Mailpit ловит всю почту стека.** Сервис `mailpit` внутри `test_internal`; SMTP Auth направлен на `mailpit:1025`, заданы `GOTRUE_SMTP_FROM` / `GOTRUE_SMTP_ADMIN_EMAIL`. Исходящих рассылок быть не может: сеть internal. Письма (recovery/confirm) читаются через UI `127.0.0.1:18025` или API `/api/v1/message/latest`.
3. **Публикация портов — через socat-прокси.** У контейнеров, подключённых только к `internal: true` сети, Docker не поднимает host port forwarding (проверено на docker 29.9.1). Поэтому `ports:` убраны с auth/rest/mailpit и добавлены сервисы `auth-local`, `rest-local`, `mailpit-local` (alpine/socat), подключённые к обеим сетям (`test_internal` + `test_edge`) и публикующие порты только на `127.0.0.1`. Сервисы данных остаются без исходящего доступа.
4. **Регрессионный тест auth-потоков** — `scripts/supabase-test-auth-flows.sh`. Прогоняет на живом стеке: signup → строка профиля с ФИО/телефоном/ролью, login/refresh/logout, отказ при неверном пароле, сброс пароля через письмо mailpit (`/recover` → `token_hash` из письма → `/verify` → смена пароля → повторный вход, старый пароль отклонён). Создаёт одного случайного тестового пользователя за прогон, не трогает production-контейнеры.
5. **Регрессионный тест ролей и RLS** — `scripts/supabase-test-rls-roles.sh`. Создаёт 4 случайных пользователя (admin/instructor/2 ученика), раскладывает роли как admin workflow (первый админ — через `session_replication_role=replica`, т.к. триггер `prevent_unauthorized_role_change` не пропускает даже service_role) и через PostgREST с реальными JWT проверяет 20 утверждений: ученик читает только свой профиль (инструкторы намеренно видны всем authenticated — выбор инструктора), не меняет чужие данные и не может назначить себе роль; инструктор видит только своих учеников; админ читает всё, управляет группами и ролями. JWT-роль всех пользователей — `authenticated`, прикладные роли живут в `public.profiles.role` и проверяются через `is_admin(auth.uid())`.

6. **Storage API и единый gateway.** Сервис `storage` (supabase/storage-api:v1.74.0, backend `file`, volume `test_storage_data`) живёт только в `test_internal`; `JWT_SECRET`/`PGRST_JWT_SECRET` — тестовый секрет, ключи — из root-only `.env`. Перед стартом storage установщик задаёт пароль роли `supabase_storage_admin` (тот же паттерн, что и для `authenticator`/`supabase_auth_admin`). Бакеты и политики создаются из `docker/test-supabase/storage-buckets.sql` (установщик ждёт готовности `/storage/v1/status` через gateway, т.к. storage-api мигрирует схему `storage` при первом старте): `avatars` и `lesson-media` — public, `student-documents` — private; 8 политик на `storage.objects`. INSERT раздельный по бакетам: `avatars`/`student-documents` — свои файлы любому authenticated, `lesson-media` — только инструкторам и админам (роль проверяется через `public.profiles`). Важно: колонка `owner` имеет тип uuid, в политиках используется `owner = auth.uid()` (каст `auth.uid()::text` даёт ошибку типа).
7. **Единая точка входа `gateway`** (nginx:alpine) маршрутизирует `/auth/v1/` → GoTrue:9999, `/rest/v1/` → PostgREST:3000, `/storage/v1/` → Storage:5000; `proxy_pass` с завершающим `/` срезает префикс, как Envoy в production-стеке. CORS повторяет production-ограничения основного API-vhost: whitelist origin'ов (HTTPS-поддомены `dvizh-school.ru` + `localhost` для разработки), точный origin вместо `*`, без credentials (supabase-js использует Bearer/apikey, не куки), методы без CONNECT/TRACE; отдельный блок для OPTIONS: `add_header` внутри `if` отменяет наследование серверных заголовков, поэтому ACAO/Vary продублированы внутри блока — иначе preflight уходит без ACAO. Наружу gateway выставляет только socat-прокси `gateway-local` на `127.0.0.1:28000`.
8. **Регрессионный тест Storage** — `scripts/supabase-test-storage.sh`. Через gateway с реальными JWT двух учеников проверяет 19 утверждений: anon читает public-бакеты и не читает private, authenticated владеет только своими объектами (upload/read/PUT-update/delete), ученик не грузит в `lesson-media` (запрет по роли), чужие объекты не читаются/не правятся/не удаляются, service_role обходит политики по дизайну, CORS-preflight выдаёт ACAO только whitelist-origin'ам без CONNECT/TRACE/credentials. Случайный суффикс имён не даёт пересечениям при повторных прогонах. Проверено на живом стеке (2026-10-16): 19/19 PASS. Подводный камень: `update()` в supabase-js — это `PUT /object/{bucket}/{path}`, отдельного маршрута `/object/update/` в storage-api v1.74.0 нет.

9. **Realtime (postgres_changes)** — сервис `realtime` (supabase/realtime:v2.134.10) только в `test_internal`; tenant `realtime-dev` seed'ится сам (`SEED_SELF_HOST`). Три неочевидных предпосылки, без которых стек падает или молчит: схему `_realtime` нужно создать до первого старта (мигратору нужна для `schema_migrations`, образ её не создаёт); `DB_ENC_KEY` строго 16 байт — realtime шифрует JWT-секрет тенанта AES-128-ECB и падает с `Bad key size` при другой длине; таблицы должны входить в публикацию `supabase_realtime`, иначе подписки регистрируются, но события не приходят (установщик добавляет `public.profiles`). Маршрутизация повторяет production Envoy: `/realtime/v1/api/` → `/api/`, WebSocket `/realtime/v1/` → `/socket/` с `Host: realtime-dev.supabase-realtime` — realtime определяет tenant по hostname и иначе отвечает `TenantNotFound`. Тест `scripts/supabase-test-realtime.sh` (node ≥ 22, global WebSocket) проверяет доставку `postgres_changes` со своей строкой и RLS-изоляцию: событие по чужому профилю пользователю не приходит. Проверено на живом стеке (2026-10-16): 3/3 PASS.

**Проверено на живом стеке (2026-10-16)**: `supabase-test-auth-flows.sh`, `supabase-test-rls-roles.sh`, `supabase-test-rls-data.sh` и `supabase-test-storage.sh` — все проверки зелёные. Подводный камень при ручных проверках: значения из root-only `.env` нужно читать с `.strip()` — хвостовой `\n` в заголовке `apikey` молча ломает авторизационный контекст PostgREST (0 строк вместо данных).

## Установка и контроль

Для ручного запуска на VDS нужны два файла из этого PR, установленная директория `/opt/driving-school-supabase-test` и осознанный review. Сценарий выполняется только один раз и отказывается от перезаписи уже существующего test volume.

Проверить отдельно `docker compose config` с test env до запуска. Не копировать рабочий `.env`.

Перед установкой желательно посмотреть, что сервисы используют только новые ресурсы и локальные порты. Не менять production Nginx/Compose. После запуска проверить ответы API, storage-сценарии и отрицательные RLS сценарии.

**Изоляция:** Docker network `internal: true` запрещает прямой внешний маршрут из test services, но Docker-группе и хостовому root доверяется полный доступ; это не криптографическая граница. Пользовательские записи из cloud архивов не импортируются.
