# Первый изолированный тест восстановления (только profiles)

## Область проверки

Одноразовый проверочный сценарий восстанавливает **только** схему и данные таблицы `public.profiles` из имеющегося snapshot `cloud-backup.dump` в отдельный кластер PostgreSQL 17.6. Он **не** переносит Auth, RLS, расширения, Storage или production данные, не тестирует вход пользователей и не подтверждает пригодность полного дампа. Результат со статусом SUCCESS подтверждает только восстановление одной таблицы.

## Безопасность и ограничения

- Образ `postgres:17.6` должен быть предварительно скачан: скрипт не тянет образы из сети.
- Тестовый контейнер: `cloud-restore-smoke-v1`; том: `cloud-restore-smoke-data-v1`. Никакой из существующих `supabase-db`, `supabase-restore-db`, `supabase-restore-data` и `supabase-restore-data-v2` не изменяется.
- `--network none`, отсутствие port bindings, `listen_addresses=''`; дамп монтируется только для чтения.
- Скрипт прекращает работу, если одноимённый контейнер или том уже существует. Не выполняет `docker rm`, `docker volume rm`, `down -v`.
- Конкретная схема `profiles` может зависеть от специальных типов и расширений Supabase. В таком случае тест безопасно завершится ошибкой: **не** отключать проверки и не запускать полный дамп с расширениями/фоновой рассылкой.
- После выполнения тестовые контейнер и том **сохраняются** для разбора. Удаление — отдельное подтверждаемое действие.

## Однократная настройка

После review и merge PR root на VDS проверяет версию скрипта и устанавливает его владельцем root в `/usr/local/sbin/supabase-restore-smoke-test` с режимом 0755. Файл не должен изменяться пользователем `deploy`.

Ограниченное правило `sudoers`:

```text
deploy ALL=(root) NOPASSWD: /usr/local/sbin/supabase-restore-smoke-test ""
```

Не выдавать группе `deploy` Docker socket и не разрешать `sudo docker`. Перед запуском нужно независимо убедиться, что скрипт на сервере соответствует рассмотренному коммиту.

GitHub Action допускается включить переменной `SUPABASE_RESTORE_SMOKE_ENABLED=true`; запуск **только вручную**. Первый запуск создаст новый тестовый контейнер/том и завершится либо количеством строк profiles, либо диагностикой зависимости. Повторный запуск без отдельной очистки не должен менять данные.

## Следующие этапы

После удачного частичного теста — полноценный изолированный restore Auth/RLS/Storage с отключёнными исходящими уведомлениями, проверка ролей и login, затем свежая синхронизация и cutover. Счётчик строк не подтверждает актуальность снимка относительно живой облачной базы.
