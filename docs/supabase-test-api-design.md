# Отдельный тестовый Supabase: безопасный переход к API

Текущее состояние: **в отдельном Docker-контейнере восстановлено только DDL public**; нет пользовательских данных. Сверены 30 таблиц, 51 функция, 60 RLS policies, 44 FK и 16 триггеров.

## Критический блокер полноценного API

Тестовый `clean-supabase-schema-lab-v1` намеренно запущен с `--network none`, без опубликованных портов и с `listen_addresses=''`. **Нельзя просто запустить рядом Auth/PostgREST/Storage и ожидать, что они подключатся**. Нельзя подключать этот контейнер к общей production Docker network или публиковать DB порт; это уничтожило бы гарантии изоляции.

Нужно спроектировать **новое тестовое Docker Compose окружение с собственной внутренней сетью, отдельными секретами JWT и DB, отдельными volumes и сервисами**. Для этого сначала определить версии образов и обязательные env параметры существующей self-hosted установки на VDS; репозиторий приложения пока не содержит соответствующий production compose файл.

### Предлагаемая архитектура

- Отдельная внутренная сеть `supabase-test-internal` и отдельный тестовый Postgres с копией **только уже созданной пустой структуры**. Не переносить архивные таблицы с данными.
- GoTrue, PostgREST, Storage в той же тестовой сети; только защищённый test gateway через localhost или отдельный HTTPS endpoint с временным ограничением доступа. Никаких соединений к `supabase-db`.
- Новые JWT secret, anon и service_role keys, новые тестовые email settings. Не использовать рабочие ключи, live SMTP, OneSignal, cron или Edge functions.
- Перед публикацией проверка владения таблицами, схемных GRANT, default privileges и RLS от ролей `anon`, `authenticated`, `service_role`.
- Отдельный тестовый admin через GoTrue API после проверки auth endpoints; только синтетические записи.
- Сборка отдельной PWA с test `VITE_SUPABASE_URL` и anon key; существующие production env и Nginx сайт не изменять.

## Проверка сейчас

`scripts/supabase-clean-test-preflight.sh` делает только чтение структуры и инвентаризацию владельцев и прав в **строго заданном изолированном** контейнере. Ни Docker сеть, ни PostgreSQL, ни схему он не меняет.

**Не считать текущий контейнер готовым API сервером.** Production cutover и PR #169 запрещены до отдельного acceptance.
