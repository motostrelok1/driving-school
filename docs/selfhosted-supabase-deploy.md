# Self-hosted Supabase — деплой через GitHub Actions

## Статус
Безопасный шаблон; **не включать продакшн-деплой до baseline и проверки на тестовой копии**.
CI проверяет наличие файлов и синтаксис скрипта, но не доказывает успешность SQL или функциональную совместимость.

## Почему нужен baseline
В `supabase/migrations` есть повторяющиеся числовые префиксы (например, 0010 и 0035).
Идентификатор миграции — **полное имя файла**, порядок — лексикографический.
В GitHub могут отсутствовать SQL-изменения, применённые вручную в Supabase Dashboard.
Запуск всех старых SQL-файлов на перенесённой базе опасен. Сначала:
1. Снять **внешний** backup облачного PostgreSQL, Storage и Auth; проверить восстановление на копии.
2. Сверить живую схему с GitHub, включая роли, grants, RLS, policies, functions, extensions, triggers, cron и storage metadata.
3. Перенести данные и проверить контрольные суммы/счётчики, авторизацию и WebSocket.
4. На клоне перенесённой БД согласовать исторический baseline; только затем записать полные имена файлов и SHA-256 в таблицу `public._deploy_migrations`. Делать это по проверенному списку, **не автоматически**.
5. Настроить внешние резервные копии и аварийный откат.
6. Установить серверный скрипт и его ограниченное sudo-разрешение; проверить ручной деплой.
7. Создать защищённое GitHub Environment `supabase-production` с approval, затем выставить vars `SELFHOSTED_DB_BASELINED=true` и `SELFHOSTED_DB_DEPLOY_ENABLED=true`.

## Предлагаемая схема
- PR: существующий `ci.yml` + `validate` нового workflow; деплой с PR не выполняется.
- Merge в main с изменениями migrations/functions: при обоих флагах и approval делается доставка по SSH.
- Пакет распаковывается на сервере. Скрипт проверяет checksum для ранее выполненных миграций, применяет только новые, при SQL-ошибке останавливается, и лишь затем обновляет Edge Functions.
- SQL применяется к Docker PostgreSQL 17, не к LMS PostgreSQL 16.
- Не открывать 5432 в интернет и не класть секреты или `.env` в GitHub.
- Edge Functions в локальном docker стеке — файловые: новые каталоги должны поддерживаться существующим роутером `volumes/functions/main`. Перенос всех шести функций и их переменных окружения тестируется отдельно. Cron/OneSignal вручную сверяется до активации.
- GitHub Actions не заменяет backup, проверку RLS и версионирование Docker-образов.

## Настройка VDS (пока НЕ выполнять до baseline)
Сначала проверить SSH-пользователя и путь `/opt/supabase`; штатный скрипт предполагает:
`/usr/local/sbin/driving-school-supabase-deploy`, установленный из `scripts/selfhosted-supabase-deploy.sh` с правами root:root 0750.
Права sudo должны разрешать только этот скрипт от выбранного пользователя деплоя; не давать неограниченный доступ.
Скрипт отказывается работать без файла-флага `/opt/supabase/.migration-baselined`, который создаётся лишь после проверенной фиксации baseline. Наличие флага само по себе не доказывает корректность импорта.
Хранить секретные конфигурации Edge Functions на VDS, не копировать их в GitHub.

## Важные ограничения
- Изменения схемы должны быть обратносуместимыми при rolling deploy; destructive migrations требуют отдельного плана.
- `pg_dump` / `pg_restore` и перенос пользователей и Storage — **отдельные этапы**, данный workflow их не выполняет.
- Внешняя ротация ранее раскрытых JWT/JWK секретов обязательна до продуктивного использования.
- После включения запустить контрольный workflow_dispatch, проверить таблицу migration ledger, Health Auth/Storage и бизнес-сценарии, затем разрешить автоматизацию.
