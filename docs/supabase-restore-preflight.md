# Проверка архива Supabase до тестового восстановления

Этот workflow **только читает** метаданные архива, Docker-сети и контейнеров. Не выполняет `pg_restore`, `docker run`, SQL или удаление томов. Не использовать для проверки фактической пригодности резервной копии: потребуется отдельное изолированное восстановление.

## Однократная настройка на VDS

Внимание: перед копированием необходимо проверить содержимое файла из PR. Установка требует root; исполняемый скрипт должен принадлежать root и не быть доступен на запись SSH-пользователю.

После слияния PR на сервере, из каталога `/var/www/driving-school` (при условии что он обновлён до соответствующего коммита):

```bash
sudo install -o root -g root -m 0755 scripts/supabase-restore-preflight.sh /usr/local/sbin/supabase-restore-preflight
```

Нужно узнать фактическое значение GitHub Secret `DEPLOY_USER` **локально на сервере** (не печатать приватный ключ и не отправлять secrets в чат). Пример установки правила с подстановкой реального имени пользователя:

```bash
sudo visudo -f /etc/sudoers.d/supabase-restore-preflight
```

Точная единственная строка sudoers:

```text
<DEPLOY_USER> ALL=(root) NOPASSWD: /usr/local/sbin/supabase-restore-preflight ""
```

Заменить `<DEPLOY_USER>` на реальное имя пользователя, не вводить угловые скобки. `""` означает запрет аргументов. Убедиться, что файл sudoers имеет права 0440 и пройдёт `visudo -c`.

Далее установить GitHub repository Variable `SUPABASE_RESTORE_PREFLIGHT_ENABLED=true`, вручную запустить Actions → Supabase — проверка перед восстановлением.

## Защита
- Не давать CI пользователю доступ к группе `docker` или общий `sudo docker`: это эквивалентно root.
- Не позволять CI перезаписывать серверный скрипт: `/usr/local/sbin/supabase-restore-preflight` всегда принадлежит root.
- Проверка выводит **только** метаданные, не выводит дамп и значения .env.
- Автоматизированное восстановление и безопасность его изоляции проектируются отдельно; пока его нет.
