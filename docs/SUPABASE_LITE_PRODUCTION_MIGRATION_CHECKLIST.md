# Чек-лист: production Driving School → собственный Supabase Lite

**Статус:** план и release gates, НЕ инструкция к немедленному переключению. 17.10.2026. Test acceptance: 26/26 UI driving cycle, browser roles, RLS/Storage/Functions/scenarios/PDD/Realtime, восстановление резервной копии; эти результаты не заменяют испытания новой production-инсталляции.

## 0. Развести два разных сценария
- **Новая автошкола:** пустой изолированный экземпляр Lite Core, **чистая прикладная схема**, ноль перенесённых пользователей и персональных данных; затем Driving School Kit и отдельно разрешённый учебный контент.
- **Миграция действующей production-автошколы:** нельзя просто заменить базу чистой — исчезнут существующие аккаунты, записи, оплаты, документы, занятия, разрешения, переписка и прогресс. Нужен отдельно согласованный перенос production DB+Storage и auth/identity/session strategy с сохранением связей и прав; этот сценарий требует подробного cutover и rollback. **Не начинать до явного решения о сохранении данных и окна переключения.**
Никаких копирований реальных данных в тестовый или общедоступный demo-проект.

## 1. Готовность Supabase Lite Core
- [ ] Независимый Compose project, DB и Storage volumes, отдельные Docker networks, новые ключи и пароли, не пересекающиеся с production/test; версионированные образы и совместимость.
- [ ] Чистая установка Core на другом VDS/новых томах: postgres/Auth/REST/Storage/Realtime/Functions/gateway, health checks, restart и независимый restore.
- [ ] Сервисные роли PostgreSQL, auth schema, RLS, schema grants и расширения проверены; публичны только HTTPS endpoints.
- [ ] TLS, DNS, CORS allowlist, Auth SITE_URL/redirect allowlist, Storage/Functions reverse proxy, WebSocket routing; отсутствие старых production/test origin в чужих окружениях.
- [ ] Установщик идемпотентен и fail-safe (смотрит на конфликт томов/сети/портов и отказывается менять существующий стек); `.env` 0600, секреты не раскрываются в логах/frontend.

## 2. Driving School Kit и миграции
- [ ] Опубликован независимый от backup пакет SQL миграций с baseline, ledger и проверкой версий: целиком schema+RLS+RPC+triggers+Storage policies; включает 0035/0040/0056 и все последующие совместимые изменения. Schema catch-up из test не заменяет clean-room миграции.
- [ ] Схемы Auth/public/storage устанавливаются в правильном порядке; после clean install подтверждаются profile trigger, bootstrap первого admin, безопасное назначение ролей.
- [ ] Тестовые/демонстрационные пользователи не попадают в production по умолчанию; администратор создаётся через защищённый setup.
- [ ] Отдельные секреты Edge, cron, SMTP, OneSignal по инсталляции. В production настоящие уведомления разрешать только после проверки маршрутов и антидубликатов.

## 3. Учебные материалы и 383 PNG
- [ ] **Блокер:** 383 изображения курса сейчас присутствуют только в сформированном `dist/` и отсутствуют в Git. Нельзя объявлять пакет курса воспроизводимым, пока проверенные исходные файлы не помещены в версионированное хранилище/артефакт релиза.
- [ ] Провести инвентаризацию: имена, размер, SHA-256, MIME, фактический источник, права на распространение; сопоставить ссылки на изображения с курсом и медиаблоками.
- [ ] Сделать версионированный архив course-media (Git LFS, release artifact или проверенный object-store с манифестом и checksum; **не** хранить реальные пользовательские файлы в публичном Git). Исключить попадание чувствительных изображений.
- [ ] Автоматизировать установку содержимого: 32 раздела, 49 публикаций, блоки и `pdd-course-media` с исправлением публичных URL на новый домен; импорт идемпотентный, без ссылок на исходный `*.supabase.co`.
- [ ] Проверить 383/383 файлов по manifest (если все действительно нужны), HTTP Content-Type/доступность и отображение страниц курса в браузере; использовать запись о версиях контента. Избегать зависимости от старого `dist`.

## 4. Почта и push — обязательные production-gates
- [ ] SMTP с реальным доставляемым письмом, HTTPS links, SPF/DKIM/DMARC и настройкой `MAILER_AUTOCONFIRM=false`; проверить signup/confirm/resend/recovery на чистой инсталляции.
- [ ] OneSignal/App ID/worker/domain настроены отдельно для нового окружения; доставку проверять с реальным согласившимся устройством; отключены тестовые cron/заглушки.
- [ ] Push до подтверждения email **не реализован**; оставлять feature flag off до выполнения отдельного проекта PR #198.

## 5. Данные действующей школы (ТОЛЬКО если выбран сценарий миграции)
- [ ] Инвентаризация схемы/таблиц/Auth identities, версий, row counts, Storage metadata и файлов, Edge secrets, приложений и требований к хранению.
- [ ] Изолированная репетиция восстановления *полной* production DB + файлов Storage с доступами 0600 и новыми томами; миграции поверх согласованного baseline. Не анонимизировать рабочие данные как метод production-переноса.
- [ ] Выбрать стратегию JWT/session: сохранение совместимого signing secret в защищённом контуре **или** принудительный relogin всех пользователей (предпочтительно при ротации секретов); отдельно проверить email recovery, identities и OneSignal subscriptions.
- [ ] Репетиция миграции и согласованная остановка записей/maintenance mode, точка синхронизации, контроль счётчиков+ссылочной целостности, файлы и права, переключение DNS/Frontend env/API URL после smoke.
- [ ] Rollback plan: фиксированное окно, старый стек неизменён до подтверждения нового, DB+Storage backup, правило восстановления записи без раздвоения данных; вернуть DNS и фронтенд на старый backend при откате.

## 6. Приёмка перед переключением
- [ ] Кросс-ролевой UI: admin→instructor→student, включение вождения, разрешения, создание слота, бронь, 2-way чат, отмена → слот open.
- [ ] Изоляция пользователей: RLS прямым REST/RPC, Storage, Realtime и Functions; тест негативных доступов student/instructor/admin.
- [ ] Импорт курса: 32 раздела, 49 публикаций, все необходимые блоки и изображения доступны из **нового** собственного Storage; нет старых URL.
- [ ] Восстановление PostgreSQL **и всех бинарных Storage объектов** в независимый project с проверкой файлов/метаданных, ролей/Auth, курса и application smoke. Ротация, мониторинг, ретенция и off-host копия.
- [ ] TLS 1.3, CORS, отсутствие секретов в Git и `dist`, журнал и алерты бэкапов, тест пожарного восстановления.
- [ ] Письменное решение о go/no-go и fallback владельца проекта, production изменение только после отдельного разрешения.

## 7. Чего не делать
Не выключать нынешний production, не чистить его БД, не удалять тома и не копировать `cloud-backup.dump` как инсталляционный seed. Не считать script `anonymize-copied-db.sql` применимым к production. Не доверять только числу записей при restore. Не публиковать старые секреты и логины.
